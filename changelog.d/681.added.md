- **One redaction point per output sink** (#681, #514, the second of two steps): every tool reply and error (with the update notice), the server instructions (with their notices), progress messages, every line the CLI prints itself (`cli/output.py` `say()`, which keeps local paths such as `nas;sid=2/config.yaml` as they are; prompts and click's own errors don't go through it) and every log record (`cli/logging_.py` `RedactingFormatter`, tracebacks included) now pass through `redact_secrets`, so a credential a call site let through is masked where the text leaves the server. A reply, error, progress message or CLI line keeps a file name or local path that only looks like a query item (`download.php?id=7&token=a1b2c3.zip`): there a `key=value` item is masked only inside a URL, while logs mask it anywhere; a reply or error that needed it logs a WARNING naming the tool, never the text. Every kind of reply content is scrubbed (an embedded resource's text, a link's URI, every `_meta`), so are an `MCPError` a tool raises and an input request, and Python warnings now go through the redacting logs, so they follow the log level (a `logging.level: error` config no longer shows them). `tests/test_redaction_e2e.py` runs the real server with `serve`'s logging at DEBUG and a log file, through Download Station's listing, details and create and a call that can't connect, with canaries for the password, a keyring device token, DSM's session, userinfo and a tracker passkey; `tests/test_redaction_sinks.py` plants credentials at each sink and fails on a direct terminal, error, progress or logging write that bypasses them (a stream held in a variable is review's to catch). `say()` also writes control characters other than tab, line feed and carriage return, and terminal escapes, visibly (`\x1b`), as config errors already did — closes #514 and #486
