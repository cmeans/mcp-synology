- **Update notices reach every module, without repeating** (#433) — closes #314. The notice went only on a File Station tool's result, so a chat using only System, Download Station or Photos tools never heard of a new version, and it told the model to run `mcp-synology --check-update`, which a chat can't do. Now:
  - **Every module:** the first tool result after the background check finds a newer version carries it, whatever the module (an error result too). The check starts with the server rather than at the first DSM login.
  - **Once a week per install:** an ordinary release is announced at most once a week, recorded per install, so connections that share one (a copy serving several NASes) say it once between them; the announcement is claimed at delivery, under the state file's lock.
  - **Security releases** are announced in every session: in the server's instructions when the previous check already knew of it, otherwise on the first tool result. A release is a security release when its CHANGELOG section starts with `**Security release:**` (read from its GitHub release).
  - **Actionable:** the notice names the command that upgrades this install (`uv tool upgrade`, `pipx upgrade`, a restart for `uvx` (with `uv cache clean` as the fallback), or `pip install -U` with this interpreter, detected from the running interpreter), links the release notes, and says how to stop the notices. `mcp-synology --check-update` gives the same text.
  - **Per-config setting:** `update_notices: all | security | off` (default `all`; env `SYNOLOGY_UPDATE_NOTICES`), per config since configs may run different installs; `off` silences every notice in the chat. YAML's unquoted `off` (read as false) works too.
  - **Outside the chat:** `serve` logs a newer version at WARNING (the MCP client's server log), and `mcp-synology check` prints it before its login check, whatever `update_notices` says.
  - The README's Updates section covers all of this, plus watching GitHub releases.

### Fixed

- **A refused login isn't sent again** (#460) — closes #447. When DSM refused the credentials (a wrong or changed password, a disabled account, 2FA needed or the device token rejected), the server tried the same login again on every tool call, and on every session error. DSM's Auto Block (on by default: 10 failed logins within 5 minutes) then blocked the computer's IP address, so a changed password could lock the user out of their own NAS, in the browser too. The refusal is now remembered: later calls get the same error without contacting DSM, which says why and what to do (`mcp-synology setup`, then `mcp-synology check`). The server tries again once the credentials change (new ones stored with `setup` are picked up while it runs) or it restarts. Transport errors aren't remembered
- **A failed re-login says why** (#460) — closes #448. When a session error led to a new login and DSM refused it, the reply was the session error ("session expired"), without the login's reason or its suggestion. It's now the login's own error
- **Parallel calls log in once** (#460) — closes #359. Tool calls sent together after the session expired each logged in again, and so did parallel first calls after the server started, each leaving an extra DSM session open until DSM's timeout. One login now runs and the others wait for it and use its session. The expired session is also no longer cleared before the new login: requests sent meanwhile went with no session and queued logins of their own
- **`upload_photos` works for an account that has never used Synology Photos** (#440) — closes #436. Such an account has no `homes/<user>/Photos` folder yet, and every upload to its personal root failed with 117 ("Photos found no such item, folder or task"), retried once to no effect. The Photos web app never meets this because it calls `SYNO.Foto.Setting.User get` at sign-in, which creates the folder for a user with no photos. Creating the user, granting the Photos privilege, logging in and the web app's other start-up reads don't; creating a Photos folder does. Now, after a 117 on an upload to the personal root, `upload_photos` makes that call once and resends the file. Verified on vdsm DSM 7.1, 7.2.2, 7.3.2 and 7.4.1. If the folder is still missing, the row says why and what to do. A 117 is no longer retried after 2 s, which never helped
- **The docs no longer call only Download Station and Photos "opt-in"** (#437) — closes #426. Every module, File Station and System included, loads only when it's listed under `modules:`, and `setup` writes File Station only; the README, CLAUDE.md and the Download Station and Photos specs now say so for every module
- **The spec check reads each tool's parameters from its own table only** (#432) — closes #429, found in QA of #428. `tests/test_module_specs.py` let the last tool section of a spec run to the end of the file, and read parameters from everything between **Parameters:** and the next bold line, so a later table row starting with a backticked name (the Storage spec's Phase 2 table, once that module is registered) or a second table after prose became a parameter. A tool section now ends at the next tool heading or `## ` heading, and parameters come from the table right under **Parameters:**. New tests cover both cases; the five specs parse as before
- **An rc install now hears of the final release** (#433) — closes #411. The version comparison split on dots, so `0.10.0rc11` didn't parse and the check reported no update; versions now order by PEP 440 (`0.10.0rc11 < 0.10.0 < 0.10.0.post1`)

## 0.10.0 (2026-10-28)

**Upgrading from 0.9.x:** 0.10.0 adds the Synology Photos module and tightens config checking. Five things to know:

- **Synology Photos is a new opt-in module** (#286): 19 tools for the personal space and Shared Space. Enable it under `modules` → `photos`, with `permission` `read` or `write`. Its upload and download tools use the same `allowed_local_paths` as the other modules.
- **A misspelled key directly under a module now stops the server** (#368). Under `modules.<name>`, anything other than `enabled`, `permission` and `settings` is a configuration error. In 0.9.x, `permision: write` was dropped silently and the module ran read-only. An unknown key inside `settings`, or an unknown module name, is a warning. Run `mcp-synology check` on your config after upgrading.
- **Each reply is sent once, as text** (#377). Tools no longer carry an `outputSchema`, and replies no longer repeat their text as `structuredContent`. A client that read `structuredContent` should read the text content instead.
- **Plain HTTP is now a WARNING in the log, and `setup` defaults to HTTPS** (#374). Existing configs keep working unchanged; `docs/https.md` covers DSM's certificate and how to turn HTTPS on.
- **Braces in custom instructions are taken literally** (#391). `custom_instructions` and `instructions_file` text no longer goes through Python's string formatting, so a brace such as `{"a": 1}` no longer stops `serve` from starting, and `{{` and `}}` are no longer escapes. If you doubled braces to get past the old crash, undouble them: they now reach the model doubled. The six template variables (`{host}`, `{port}` and the rest) still work.

## 0.9.0 (2026-10-17)

**Upgrading from 0.8.x:** long File Station operations now hand off instead of stopping, and Download Station's torrent files are confined to the allowed local folders. Four things to know:

- **Deletes, copies, moves and restores hand off after 30 s by default** (#251). A call that's still running then returns a handle, the NAS keeps working, and the new `file_task` tool checks on it or stops it. In 0.8.x the operation was stopped when its timeout ran out. `delete_timeout` and `copy_move_timeout` now mean how long a call waits before handing off: 30 s when unset (they used to fall back to `async_timeout`, 120 s), and at most 600 s whatever the setting. `async_timeout` now applies only to `search_files` and `get_dir_size`.
- **`create_download` reads torrent files only from the allowed local folders, and only `.torrent` and `.nzb` files** (#259, a security fix). By default that's your Downloads folder. A torrent file elsewhere is refused until you list its folder in `allowed_local_paths`, under `downloadstation` → `settings` or at the new top level. Without a top-level list, a module's own list replaces the Downloads default, so include `~/Downloads` if you still want it. Magnet links and URLs aren't affected.
- **A new top-level `allowed_local_paths`** applies to every module, and each module's own list adds to it (#259). Existing configs behave as before while it's unset.
- **`list_shares`, `list_files` and `search_files` no longer take `additional`** (#240). It never added anything to their tables; leaving out a field they show (`size` or `time` for files, `real_path`, `owner` or `volume_status` for shares) only blanked those columns. They now always fetch what they show. Per-file owner, permissions and real path are still available from `get_file_info`.

### Added

- **Allowed local folders for every module** (#259) — a top-level `allowed_local_paths` lists the local folders that every module's local-path tools may use: File Station's `upload_file` and `download_file`, and Download Station's `create_download` torrent files. A module's own `allowed_local_paths` (in its settings) adds to it. While the top-level list is unset nothing changes: each module's own list replaces the default, your Downloads folder. The LOCAL PATHS server instructions name each module's folders; the payload grows from 17,327 to 17,582 characters
- **`file_task` follows up on long operations** (#251) — a new File Station tool (WRITE tier, so File Station now has 15 tools: 7 READ + 8 WRITE), annotated `destructiveHint=true` because a stop can leave a move or delete half done. With a handle from a delete, copy, move or restore reply, `action="status"` shows the operation's progress and how long it has been running, saying that a count that hasn't moved doesn't mean it's stuck (a delete counts finished items, and one large file can take many minutes), or its final result in the original tool's shape once it finishes, if DSM still has it (a task that finished or was stopped with no status read to catch it is reported as no longer running, naming its path, and a stop of it says nothing was stopped); the running time comes from the task ID, which begins with the start time; `action="stop"` stops it (it may then be partly done); a stop without a handle is `invalid_parameter`, never a list. Without a handle it lists this DSM user's running delete, copy and move tasks with their handles, which helps in a new chat or after a restart. A handle is checked before any DSM call (`invalid_parameter` otherwise), and its prefix picks the API, so it can't reach anything but that user's Delete or CopyMove tasks. A stop reads the task's status first, because CopyMove `stop` answers success for any task ID, so `file_task` never claims to have stopped a task that had already finished. The server remembers the last 50 handed-off tasks for 24 hours (in memory only) so it can give the full result after DSM forgets a finished task. If DSM doesn't answer the recycle-bin check when a delete's result is built, the result is still given, saying the recycle-bin setting couldn't be checked. On the first File Station call after the server starts, it lists the user's running tasks once and, if any are running, adds a one-time note with their handles to that reply. A `file_task` reply about one handle leaves that task out of the note, and a `file_task` list doesn't add the note at all
- **Progress notifications for deletes, copies, moves and restores** (#251) — while a call waits, it sends MCP progress notifications (about one every 2 s, only when the numbers change), e.g. "Deleting /Backups/X: 124,219 of 200,400 items"; copies and moves count bytes. While DSM is still counting, a heartbeat with no total is sent, so a client's idle timer doesn't run out. The progress value increases with every notification, as MCP requires, including heartbeats and the later paths of a multi-path call (which share one progress token), and a failing notification never interrupts the operation
- **README documents the File Station settings** (#251) — a new "File Station settings" section lists the timeouts, what the delete/copy/move/restore wait means, and the local-path and listing settings, which were documented only in the config spec and `examples/`. It also explains the MCP client's own idle timeout (Claude Code's `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`, or a per-server `timeout`), which `get_dir_size` and `search_files` can hit because they don't send progress yet; `docs/error-codes.md` covers it under `timeout`

### Changed

- **Long deletes, copies, moves and restores keep running on the NAS** (#251) — closes #245. `delete_files`, `copy_files`, `move_files` and `restore_from_recycle_bin` used to stop the DSM task when their timeout ran out, abandoning a multi-hour delete partway. Now a task still running when the wait ends is handed off: the NAS keeps working, and the reply is a normal (non-error) result saying it's still running, with its progress and a handle such as `delete:FileStation_179219158016597225` for `file_task`. In a multi-path call, the paths after it aren't started and are listed as "Not started". A path that already has a running task of the same kind isn't started a second time; the reply gives that task's handle. `delete_timeout` and `copy_move_timeout` now set how long the call waits before handing off: **30 s** when unset (they used to default to `async_timeout`, 120 s, which now applies only to search and `get_dir_size`), and capped at **600 s** whatever the setting, below known client timeouts. A status request that gets no answer during the wait (a network timeout or dropped connection, e.g. DSM stalled by a huge delete) or an answer that can't be read (e.g. a login page from a captive portal or reverse proxy) hands the task off too: the reply says the NAS stopped answering, or that its status reply couldn't be read (naming only the error type), that the operation is probably still running and shouldn't be started again, and gives the handle (maintainer decision 2026-10-17). A canceled call, including a client's own timeout, still stops the task, and so does a DSM error while polling. A stop request (from `file_task` or after a DSM error while polling) waits up to 90 s for DSM's answer, because DSM 7.1 sometimes answers a Delete `stop` only after about 60 s although the stop takes effect at once; only the read timeout is raised, so an unreachable NAS still fails at the usual connection timeout. An operation that finishes within the wait returns the same result as before. The server instructions gain a short "Long operations" section telling the model not to poll in a loop, start an operation again while it runs, or stop and restart one because its progress looks slow; the payload a model receives grows from 15,831 to 17,327 characters
- **`restore_from_recycle_bin` waits `copy_move_timeout`** (#251) — it runs DSM CopyMove tasks but used `delete_timeout`
- **`list_shares`, `list_files` and `search_files` no longer take `additional`** (#240) — they accepted DSM metadata fields (`owner`, `perm`, `real_path`, `type`, `mount_point_type`, …) that their tables never show, so a request for them silently did nothing. ### Fixed

- **Download Station's `create_download` reads only `.torrent` and `.nzb` files inside the allowed local folders** (#259) — closes #257. `torrent_file_path` used to upload any file the server's user could read to the NAS (a mistaken or prompt-injected call could send SSH keys or credentials), and its "not found" error revealed whether any local path existed. - **CI label automation finds a PR by its head commit, not its branch name** (#241) — `pr-labels-ci.yml` looked up the PR for a finished CI run by branch name whenever GitHub didn't link one, which is always the case for fork PRs. A failed PR lookup now fails the job instead of passing as "no PR", and fork PRs opened from the fork's own `main` branch get labeled too (the default-branch guard is gone; `event == 'pull_request'` already excludes pushes to `main`) — closes #203
- **Ready for QA now waits for vdsm** (#241) — label automation promoted a PR to Ready for QA as soon as the `CI` workflow passed, while the separate `vdsm` workflow was still running or had failed: vdsm's jobs are `continue-on-error`, so even a finished vdsm run reports success when a job failed, and nothing marked the PR CI Failed. `pr-labels-ci.yml` now runs when either `CI` or `vdsm` completes and checks both workflows' jobs on the PR's head commit: Ready for QA only when every job passed (CI's report-only `tool-quality` aside), CI Failed as soon as one failed (also replacing a Ready for QA label), and no change while one is still running. Removing Dev Active (`pr-labels.yml`) uses the same check; that workflow now asks for `actions: read` instead of the unused `checks: read`. `CONTRIBUTING.md` says promotion needs both CI and the vdsm integration tests
- **QA Gate no longer stays green on a commit pushed after QA Approved** (#242) — `qa-gate.yml` decided from the push event's label list, which still held **QA Approved** for a couple of seconds until `pr-labels.yml` removed it, and that removal never re-ran the gate, so the new, unreviewed commit kept a green QA Gate. A new commit (opened, synchronize, reopened) now always gets **pending**. On a label change the gate reads the PR's current labels and head from the API, marks success only when **QA Approved** is on the current head, and ignores a label event for a commit that's no longer the head. ## 0.8.0 (2026-10-16)

**Upgrading from 0.7.x:** mcp-synology now runs on the mcp 2.x SDK (`mcp>=2.3,<3`, #226). Tools, their schemas and their results are unchanged, and clients on both the 2025-11-25 and 2026-07-28 protocol versions connect. Three things to know:

- **Upgrade with your installer as usual** (`uv tool upgrade mcp-synology`, or a new `uvx` run). If you installed mcp-synology into an environment shared with another package that requires `mcp<2`, the two can no longer be installed together; give mcp-synology its own environment.
- **Login failures now arrive as structured errors.** In 0.7.x a login failure, or another DSM error raised while connecting, reached the model as plain text, such as `Error executing tool <name>: No such account or incorrect password`, and DSM login errors lost their suggestion. It's now the structured JSON error other tools already return: `auth_failed` with its suggestion (check the username and password, or run `mcp-synology setup` when no credentials are stored) and `help_url`, or the error's own code. The `Error executing tool <name>: ` prefix is unchanged.
- **Credentials stay out of URLs and error text.** The login is now sent as a POST (#236), so the password, OTP code and device token no longer appear in request URLs, where DSM's or a reverse proxy's access logs could record them. And an HTTP error status from DSM or a proxy (#233) is now a structured `unavailable` error; 0.7.x sent the model the full request URL, including the password on login or the session ID on other calls. If a reverse proxy in front of DSM only allows GET requests, allow POST to the `SYNO.API.Auth` endpoint (`/webapi/entry.cgi`).

### Added

- **PNG server icons** (#230) — closes #228, #229. `serverInfo.icons` now lists light and dark 128px PNGs, embedded as `data:` URIs, alongside the hosted SVGs, which now declare `sizes: ["any"]` (scalable). The MCP spec requires clients that display icons to support PNG but SVG only SHOULD be supported, and lets them refuse icon URLs from another origin, which a stdio server doesn't have. The `initialize` response grows by about 20 KB; tool payloads are unchanged. claude.ai and Claude Desktop don't show it yet: they take a local server's icon only from a desktop extension's manifest (anthropics/claude-ai-mcp#152).

### Changed

- **Requires mcp 2.x** (#226) — `mcp>=2.3,<3`; was `>=1.15.0,<2`. The server is now built on `MCPServer`, mcp 2.x's renamed `FastMCP`. Tool names, schemas, descriptions and results are unchanged: the payload a model receives is the same size (16,039 chars measured, 20,911 for the full `tools/list`), and clients on the 2025-11-25 and 2026-07-28 protocol versions both connect. Schema compaction and the reported server version now use documented 2.x APIs instead of private SDK attributes. A login failure, or another DSM error raised while connecting, is now a structured error: `auth_failed` with its suggestion (check the username and password, or run `mcp-synology setup` when no credentials are stored) and help URL, or the error's own code. 0.7.x sent it as plain text, and DSM login errors lost their suggestion; mcp 2.x on its own would send only "Error executing tool <name>". Other errors keep their message, as in 0.7.x. A crash in a tool is logged at ERROR with its traceback; an anticipated error (a structured one, or a DSM error) at INFO without one. Installing alongside a package that needs `mcp<2` is no longer possible — closes #114
- **Login is sent as a POST** (#236) — `SYNO.API.Auth` login used a GET, so the password (and, with 2FA, the OTP code and device token) was in the request URL, where DSM's web server and any reverse proxy in front of it can log it. The login, including `mcp-synology setup`'s 2FA login, now sends them in a form POST body; the session ID and every other call are unchanged. Verified on DSM 7.1 and 7.2.2 — closes #235

### Fixed

- **DSM HTTP errors no longer expose the password or session ID** (#233) — when DSM, or a proxy in front of it, answered with an HTTP error status (a 502 during login, a 500 on a tool call), the error text sent to the model contained the full request URL, including `passwd=` on login or `_sid=` on every other request. With mcp 2.x (#226) the server log's ERROR traceback contained it too. Such a failure is now a structured `unavailable` error naming the status, API and method (`SYNO.FileStation.List/list_share: DSM answered HTTP 500.`), retryable for a 5xx, and no exception holds the URL. As a backstop, any URL in an unexpected exception's text is redacted before the model sees it. `mcp-synology check` still reports an HTTP error on the API info query as not a DSM API response; an HTTP error during login is now reported as an authentication failure naming the status. The "No credentials found" login error now carries its `mcp-synology setup` hint as a `suggestion`, so the structured `auth_failed` error lists it in that field — closes #232

The tools ignored that, so a copy that copied nothing read as success, and a move that moved nothing claimed its source had been removed. - **Unknown shared folders get a clear error instead of DSM 900 or 1100** (#173) — `validate_share_path()` existed but was never called, so a path naming a share that doesn't exist reached DSM and came back as "Unexpected server error" (delete) or "Insufficient filesystem permissions" (create_folder). Share names match case-insensitively, as DSM does (`/VIDEO/...` for `video`). If DSM won't list shares, DSM's own error stands — closes #160
- **`download_file` no longer destroys or escapes local files** (#178).
  - **A failed download deleted the file it would have replaced.** With `overwrite=true`, any DSM error (a missing NAS path, say) ran a cleanup that unlinked the local destination even though nothing had been written to it, and a connection dropped mid-stream had already truncated it. `DsmClient.download` now streams to a temp file (`.mcp-synology-*.part`) in the destination folder and renames it into place only after the whole body arrives; on any failure it removes the temp file and leaves the destination untouched. The tool no longer deletes the destination on failure.
  - **`filename` could write outside `dest_folder`.** It was joined onto the folder unchecked, so `../x` wrote to the parent and an absolute name replaced the folder entirely. The local name, whether from `filename` or the NAS path, must now be a plain file name: no `/` or `\`, not `.` or `..`, no NUL, and no drive (`D:x`, which on Windows replaces the folder too). Anything else is refused with `invalid_parameter` before the NAS is contacted, and a final check refuses any name whose file wouldn't land directly in `dest_folder`.
  - **`overwrite=false` now holds to the end.** The finished file is published so it never replaces a local file that appeared while the download was in progress (another call, another process); that's `already_exists`. With `overwrite=true` the replaced file keeps its permissions. The download is flushed to disk before it's moved into place. Replacing a file now needs free space for both copies until the rename, and a hard crash mid-download can leave a `.mcp-synology-*.part` file in the destination folder.
  - **`download_file` no longer claims `readOnlyHint`.** It stays in the READ tier, since it only reads the NAS, but it writes to this machine and can replace a local file, so it's now annotated `readOnlyHint=false`, `destructiveHint=true`. ## 0.5.0 (2026-04-10)

### Changed

- **Error responses are now structured JSON envelopes with `isError=true`** (#9)
  - Tool errors previously returned human-readable strings like `[!] List files failed: ...`. They now raise `ToolError` with a JSON envelope:
    ```json
    {
      "status": "error",
      "error": {
        "code": "not_found",
        "message": "List files failed (DSM error 408): No such file or directory",
        "retryable": false,
        "suggestion": "Use list_files or search_files to find the correct path.",
        "help_url": "https://github.com/cmeans/mcp-synology/blob/main/docs/error-codes.md#not_found"
      }
    }
    ```
  - The MCP SDK wraps this in a `CallToolResult` with `isError=true`, which is the correct protocol signal for tool failures. Clients that only display text content see the JSON directly; clients that key off `isError` now get proper failure signaling.
  - All 13 possible `code` values are documented in [`docs/error-codes.md`](docs/error-codes.md), with per-code sections covering symptoms, causes, retryability, and concrete fixes.
  - This is a client-visible behavior change. Any client that was pattern-matching the old `[!] ... failed:` text format will need to update — parse the JSON envelope instead, or key off `isError` at the MCP protocol level.

### Added

- **`ErrorCode(StrEnum)` in `core/errors.py`** — single source of truth for every code the server can emit. `error_response(code: ErrorCode)` is typed so call-site typos become mypy errors rather than silent envelopes with missing `help_url`.
- **`docs/error-codes.md`** — 12-section reference covering every surfaceable `ErrorCode` member. Each section has root causes, fix steps with specific DSM control-panel paths, and explicit retryability statements. `session_expired` is intentionally omitted (auto-retried by the core client; never surfaced to users).
- **Multi-invariant drift test** (`tests/core/test_help_urls.py`) — enforces that `ErrorCode` ↔ `HELP_URLS` registry ↔ `docs/error-codes.md` anchors stay in sync in all directions. Adding a new code without its doc section, or renaming a section without updating the registry, fails CI.
- **`errno.ENOSPC` detection** in `download_file` OSError fallback — replaces locale-dependent substring matching on error text, so local disk-full is correctly reported as `disk_full`/`retryable=True` regardless of OS language or DSM version.
- **Unit test coverage** for `modules/system/info.py` and `modules/system/utilization.py` — both modules previously had no unit tests (13% coverage), now at 99–100%.

### Fixed

- **`unavailable` `retryable` semantic is now consistent across modules** — `system/utilization.py` previously reported `retryable=False` while `system/info.py` reported `retryable=True` for the same condition ("API responded but returned no data"). Both now use `retryable=True` with an inline comment explaining the transient-condition rationale.
- **`download_file` disk-full is now reported with the same code in both detection paths** — the pre-flight branch (via `shutil.disk_usage`) and the OSError fallback previously disagreed: pre-flight emitted `disk_full`/retryable=True, fallback emitted `filesystem_error`/retryable=False despite a "Free space on the local disk" suggestion. Both now emit `disk_full`/retryable=True when disk-full is the actual cause.
- **`error_response()` is safe against non-JSON-serializable `value` arguments** — `json.dumps(..., default=str)` prevents a future caller passing `bytes` or a custom object from crashing the error handler mid-envelope.
